# RELEASE.md — чек-лист выпуска FOREST's Proxy Auto-updater

Внутренний документ для владельца репозитория. Порядок выпуска версии 1.0.0
по шагам, с командами. Стиль — рабочий: что сделать, чем проверить, что должно
получиться. Никаких обещаний и маркетинга.

Команды даны для **cmd.exe / PowerShell** (Windows). Те, что помечены
`# git-bash`, лучше выполнять в Git Bash.

---

## 0. Где что лежит (чтобы не искать при следующем выпуске)

| Что | Файл |
|---|---|
| Версия приложения (в ресурсах exe) | `packaging\version_info.txt` |
| Версия Linux-пакетов | `packaging-linux\lib\common.sh` (`VERSION`, переопределяется `FOREST_PKG_VERSION`) |
| Версия ядра Xray (вшито в exe) | `packaging\core_version.txt`, `packaging\core.lock.json` |
| История изменений | `CHANGELOG.md` |
| Сборка | `packaging\build.bat` → `packaging\build.ps1` |
| Спек PyInstaller | `packaging\ForestProxyUpdater.spec` |
| Результат сборки | `packaging\dist\ForestProxyUpdater.exe` (+ `.sha256`, `build-report.json`) |
| Заметки о выпуске | `docs\RELEASE-NOTES-<версия>.md` |

Версия приложения объявлена в **двух** местах, и они обязаны совпадать:
`packaging\version_info.txt` (ресурсы exe — `filevers`/`prodvers` = `1, 3, 0, 0`,
`FileVersion` = `1.3.0.0`, `ProductVersion` = `1.3.0`) и
`packaging-linux\lib\common.sh` (`VERSION="1.3.0"` — имя и версия Linux-пакетов).
В коде `src\*.py` константы версии нет — править её там не нужно.
Версия ядра Xray (`core_version.txt`) к версии программы отношения не имеет.
Расхождение этих двух файлов уже приводило к тому, что сборки помечались и 1.3.0, и 1.3.1;
перед выпуском сверять оба (`grep -n VERSION packaging-linux/lib/common.sh` и
`grep -n "filevers\|ProductVersion" packaging/version_info.txt`).

## 1. Обновить версию

1. В `packaging\version_info.txt` поставить нужные значения:
   - `filevers=(1, 3, 0, 0)` и `prodvers=(1, 3, 0, 0)`;
   - `FileVersion` = `1.3.0.0`, `ProductVersion` = `1.3.0`.
2. В `packaging-linux\lib\common.sh` — та же версия в `VERSION` (по умолчанию).
3. В `CHANGELOG.md` должна быть секция релиза `## [1.3.0] — 2026-10-18`
   (формат Keep a Changelog).
4. Проверить, что в `packaging\core_version.txt` стоит актуальный релиз ядра
   (`v26.3.27`) и он совпадает с `packaging\core.lock.json` (`release`).
   Обе строки обновлять вместе.

## 2. Пересобрать `.exe`

Из корня репозитория:

```
packaging\build.bat
```

Скрипт идемпотентный: поднимет `packaging\.build-venv`, поставит PyInstaller,
при отсутствии докачает ядро Xray (`fetch_core.py`) и иконку (`make_icon.py`),
соберёт onefile-`.exe` по спеке и положит в `packaging\dist\`.

Полезные варианты (по необходимости):

```
packaging\build.bat -Clean     :: снести .build-venv, build\, dist\ и собрать с нуля
packaging\build.bat -NoVenv    :: ставить PyInstaller в системный Python
```

После сборки проверить, что появились:

- `packaging\dist\ForestProxyUpdater.exe`;
- `packaging\dist\ForestProxyUpdater.exe.sha256` (для приложения к релизу);
- `packaging\dist\build-report.json` (размер, SHA-256, версия ядра, версия
  PyInstaller — удобно для описания релиза).

На 1.0.0 ожидаемый результат сборки:

- размер `30 709 514` байт (`29.29` МиБ);
- SHA-256 `06dbfc2a46820b1106177a5f269840d33108a99085aa478f197e3742b21bb27d`;
- ядро Xray `v26.3.27`, PyInstaller `6.22.3`, onefile, без консольного окна.

> SHA-256 между сборками может отличаться (порядок обхода каталогов при
> упаковке архива). Это нормально: важен воспроизводимый процесс и одинаковое
> содержимое, а не побитово идентичный файл. В описании релиза указывать
> SHA-256 **именно приложенного** файла, взяв его из `.sha256`/`build-report.json`.

## 3. Прогнать автотест собранного `.exe`

Запускать **из каталога, где лежит `config.example.json`** (корень репозитория
подходит):

```
ForestProxyUpdater.exe --selftest --config config.example.json
```

Если запускаете из другого каталога — дать явный путь:

```
packaging\dist\ForestProxyUpdater.exe --selftest --config config.example.json
```

Что должно быть: заголовок с разделами 1–9 и финальная строка
`ВСЕ ПРОВЕРКИ ПРОЙДЕНЫ`. Автотест **не** лезет в сеть, **не** трогает
системный прокси и **не** занимает боевые порты (10808/10820/10810–10830).

Дополнительно проверить, что exe вообще стартует и находит ядро:

```
ForestProxyUpdater.exe --status --config config.example.json
```

Ожидаемо: `Режим: standalone`, найден путь к ядру Xray (внутри распаковки
onefile), строки «Ядро не запущено», «Серверов в пуле: 0», состояние
системного прокси и корень `%LOCALAPPDATA%\ForestProxyUpdater`.

## 4. Факт-лист проверки перед публикацией

Проверяется в первую очередь. Это то, чего в репозитории быть **не должно**.

### 4.1. Что не должно попасть в репозиторий

**Личные данные и рабочее состояние:**

- `config.json` — рабочий (личный) конфиг. В репозитории только
  `config.example.json`;
- каталоги `state/` и `logs/` (в том числе `state\backups\`, `state\bodies\`);
- `*.log`, `*.pid`;
- кэши серверов: `pool_cache.json`, `lastgood_servers.json`,
  `subscription_base64.txt`, `cf_ranges.json`;
- любые IP-адреса владельца, абсолютные пути вида `C:\Users\<имя>\...`,
  имена машин, сетевые шары (`\\server\share`), имена пользователя в
  путях/логах.

**Артефакты сборки и мусор:**

- `__pycache__/`, `*.py[cod]`, `*.egg-info/`, `.venv/`, `venv/`;
- `build/`, `dist/`, `*.spec` (кроме `packaging\ForestProxyUpdater.spec`, он
  отслеживается), `packaging\build/`, `packaging\dist/`;
- `packaging\.build-venv/`;
- `packaging\vendor/` (ядро и zip Xray — тяжёлые бинарники, в git не нужны);
- `.idea/`, `.vscode/`, `Thumbs.db`, `desktop.ini`.

Всё перечисленное уже закрыто `.gitignore` и `packaging\.gitignore`. Проверка
ниже — на случай, если файл попал в индекс раньше, чем в игнор.

### 4.2. Как проверить — короткими командами

Запрещённые **файлы** ищутся в списке отслеживаемых путей (`git ls-files`),
личные **данные** — в содержимом отслеживаемых файлов. Команды проверены на
текущем репозитории; ожидаемый вывод указан.

**A. Рабочее дерево + запрещённые файлы в индексе:**

```
git status --short ; echo ---tracked--- ; git ls-files | grep -E '(^|/)(config\.json$|state/|logs/)|\.(pid|log)$|__pycache__|pool_cache\.json$|lastgood_servers\.json$|subscription_base64\.txt$|^packaging/(build|dist)/|\.build-venv'
```

Ожидаемо: после маркера `---tracked---` — **пусто**. Строки до маркера — это
незакоммиченные правки (нормально при подготовке), среди них не должно быть
`config.json`, `state/`, `logs/`, `*.pid`, `*.log`.

**B. Личные пути и имя пользователя в содержимом:**

```
git ls-files -z | xargs -0 grep -nIE '[A-Za-z]:\\(Users|Temp|Projects|Desktop)|\\\\[A-Za-z0-9._-]+\\[A-Za-z0-9._$-]+|\\[A-Za-z0-9._-]+\\'
```

Ожидаемо: **пусто** (ни `C:\Users\...`, ни сетевых шар вида `\\сервер\шара`, ни
имени пользователя в путях).

**C. IP-адреса (loopback отброшен):**

```
git ls-files -z | xargs -0 grep -nIoE '([0-9]{1,3}\.){3}[0-9]{1,3}' | grep -vE '127\.0\.0\.1|0\.0\.0\.0' | sort -u
```

Ожидаемо — только неличные совпадения:

- диапазоны подсетей в `src\netfilters.py` (`104.16.0.0`, `172.64.0.0` и т. п.);
- публичные DNS в `src\clientwrite.py` и `src\clientwrite_v2rayn.py`
  (`1.1.1.1`, `8.8.8.8`, `77.88.8.8`, `77.88.8.1`);
- тестовые заглушки в `src\selftest.py` (`1.2.3.4`, `5.6.7.8`, `9.9.9.9`,
  `10.0.0.1`).

Личных адресов быть не должно.

**D. Убедиться, что личные файлы именно игнорируются** (а не «просто не
добавлены»):

```
git check-ignore -v config.json state/logs
```

Должны печататься правила из `.gitignore` (строки вида
`.gitignore:6:config.json  config.json`).

### 4.3. Отдельно проверить бинарный артефакт

Сам `.exe`, который вы приложите к релизу, репозиторий не засоряет (он в
`packaging\dist\`, а тот игнорируется). Прикладывать его нужно как **asset
GitHub Release**, не коммитить в git.

## 5. Закоммитить

Убедиться, что `git status` показывает ровно то, что нужно (см. раздел 4), затем:

```
git add -A
git status --short
git commit -m "Release 1.3.0"
```

В коммите не должно быть `config.json`, `state/`, `logs/`, `*.pid`, готовых
артефактов (`.exe`, `packaging-linux/out/`) и личных путей.

**Куда пушить.** Публичный репозиторий — это ремоут **`proxy`**
(`github.com/FORESTmg/proxy-auto-updater`, ветка `main`);
ремоут `origin` указывает на **приватный** репозиторий и для выпуска не используется.

```
git push proxy main
```

Проверить, что репозиторий остался публичным и описание нейтральное:

```
gh api repos/FORESTmg/proxy-auto-updater --jq '{description,private,visibility,default_branch}'
```

## 7. Создать GitHub Release и приложить все артефакты

Набор файлов — как в прошлых выпусках (9 артефактов, к каждому `.sha256`,
плюс сводная `SHA256SUMS`): `ForestProxyUpdater.exe`, `forest-ui.exe`,
`forest-proxy-updater-linux-x86_64`, `forest-ui-linux-x86_64`, `.deb`, `.rpm`,
Arch `.pkg.tar.zst`, `.tar.gz`, `AppImage`.

```
gh release create v1.3.0 --repo FORESTmg/proxy-auto-updater ^
   --title "v1.3.0 — ..." ^
   --notes-file "C:/Users/<user>/.../rel130/RELEASE-NOTES-1.3.0.md" ^
   "C:/Users/<user>/.../rel130/*"
```

Пути для `gh.exe` — только в форме `C:/...` (MSYS-путь `/c/...` он не принимает).

Правила:

- прикладывать **собранные файлы**, а не временные артефакты сборки;
- имя тега и версия в заголовке должны совпадать (`v1.3.0` / `1.3.0`);
- каждый SHA-256 — от **того самого** приложенного файла; после публикации
  сверить список ассетов через API (имена и размеры), а не только вывод команды;
- артефакты в git не добавляются — они живут только в релизе.

## 8. Что писать в описании релиза

Коротко и по фактам (полный текст — `docs\RELEASE-NOTES-1.0.0.md`, его в том
числе принимает `--notes-file`):

1. **Что это** — 1–2 предложения: автоподбор и переключение прокси в Windows,
   по умолчанию standalone (без v2rayN).
2. **Требования** — Windows 10+, права администратора не нужны. Ядро Xray
   (`v26.3.27`) и гео-базы уже вшиты в `.exe` — отдельно ставить нечего.
3. **Что нового в 1.0.0** — пункты из `CHANGELOG.md` (два режима, свой пул и
   балансировщик Xray, сторож, автопереключение, трей с меню, страховка размера
   пула).
4. **Установка** — скачать `.exe`, запустить; Windows покажет предупреждение о
   неподписанной программе (см. ниже).
5. **Удаление** — запустить с `--uninstall`: останавливает ядро, возвращает
   системный прокси в исходное состояние, убирает автозапуск, ярлык и каталог
   программы.
6. **Прямое предупреждение** — программа намеренно меняет системный прокси
   Windows и запускает процесс `xray.exe`; бесплатные серверы нестабильны; для
   законного использования.
7. **Проверка** — SHA-256 приложенного файла.
8. **Лицензия** — GPL-3.0-only.

Не обещать надёжность, скорость и анонимность, которых программа дать не может.

## 9. Почему `.exe` не подписан и что такое SmartScreen

Сборка **не подписывается цифровой подписью**: у проекта нет сертификата
подписи кода, а сертификат — платный и привязан к юрлицу/личности. Поэтому
Windows и часть антивирусов будут предупреждать о запуске.

Что увидит пользователь: окно **SmartScreen** «Windows защитила ваш компьютер»
с кнопкой «Подробнее → Выполнить в любом случае». Это ожидаемо для
неподписанной программы, которая (а) меняет параметры прокси в реестре и (б)
запускает другой исполняемый файл — по этим признакам эвристика и срабатывает.

Что с этим делать (и чего не делать):

- **Не** обещать, что предупреждения не будет — это будет неправдой.
- В описании релиза и в README прямо сказать: программа не подписана, поэтому
  SmartScreen предупредит; сомневаетесь — соберите `.exe` сами из исходников
  (`docs\BUILDING.md`) и прочитайте код (исходники открыты, GPL-3.0, без
  сторонних Python-зависимостей).
- Приложить SHA-256, чтобы скачанный файл можно было сверить с тем, что
  собирал владелец:

```
certutil -hashfile packaging\dist\ForestProxyUpdater.exe SHA256
```

  Хэш должен совпасть с содержимым `packaging\dist\ForestProxyUpdater.exe.sha256`.

- Если в будущем появится сертификат подписи кода — добавить шаг
  `signtool sign` в `packaging\build.ps1` после сборки; до тех пор подпись —
  вне проекта.
